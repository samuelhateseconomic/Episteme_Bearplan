## Acceptance scenario and affected records

Create/rename a project, create/edit a task and subtasks with notes, deadline and
estimate, complete/reopen leaf work, add additional work, and restart without
losing identities or fields. Parent completion follows children. Leaf totals count
each work item once. Invalid input, invalid relationships and failed saves leave
prior data intact and give useful errors. A v1 database upgrades without changing
foundation task IDs, titles, timestamps or revisions. Removing the last child
returns an incomplete task with explicit completion control.

Affected records: projects, tasks, schema_migrations. Domain functions own all
validation and mutations, use serialized `Database.write()` transactions, and own
completion/progress rules. Routes validate request shape and call those functions.
No applied SQL migration was edited during the takeover; `0002` was retained.

  preserves timestamps, revision and the parent's derived completion instant.

  task list and displayed by the interface. Parent containers never add a work item.

## Operator demonstration checklist

1. Run `python3 launch.py`; verify the existing foundation task remains in Inbox.
2. Create and rename a course project. Add a task and two subtasks, then edit titles,
   notes, deadlines and estimated minutes on both levels.
3. Complete one child, then the last: check 1/2 then 2/2 progress and derived parent
   completion. Reopen a child and add unfinished additional work; parent reopens.
4. On a disposable example, Edit → Remove subtask → Confirm removal until none
   remain. The parent must become incomplete with an enabled completion checkbox.
5. Restart, verify edits/completion remain, narrow the window and try the controls
   with the keyboard. Report any friction or failed expectation before the next build.
